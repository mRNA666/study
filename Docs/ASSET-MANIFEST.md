## 8. 文件放哪里

### 8.1 磁盘上：两棵树，不要混

```
E:\UEProjects\myproject\
│
├─ Content\                        ← UE 里的资产（.uasset），由编辑器导入产生
│
├─ RawAssets\                      ← ★ 你手工准备的东西全放这里（UE 不会自动扫）
│   ├─ Characters\                    .fbx + 贴图 + 骨骼说明
│   ├─ Vehicles\
│   ├─ Props\
│   ├─ Textures\                      原始 .png/.tga
│   ├─ Audio\                         .wav
│   └─ Source\                        可编辑源文件（.blend / .psd / .spp）
│
└─ Docs\                           ← 文档（PRD、本清单）
```

**为什么 RawAssets 必须在 Content 外面**：放进 `Content` 的 `.fbx` 会被 UE 当成资产导入，还会污染版本库。原始文件永远待在 `RawAssets`，导入后的 `.uasset` 才进 `Content`。

## 10. 三个必须先解决的问题（都在资产之外）

**① D 盘只剩 10.3 GB。** UE 的 `DerivedDataCache` 加打包产物能轻松吃掉几十 GB。建议把整个工程搬到 **E 盘**（还有 122.8 GB），或者至少把 DDC 用环境变量指到 E 盘。**这件事建议现在就做，越晚越麻烦。**

**② 中文字体没准备。** UE 默认字体不含中文，所有 UI 会显示成方块。需要一套 Noto Sans SC 之类的字体并做成 Font Asset。

**③ 工程是纯空模板。** `Content` 里连 UE 自带的 Manny/Quinn 都没有——意味着第 5 步写玩家控制器时**没有可控制的角色**。要么从 ThirdPerson 模板拷一份小人过来当占位，要么等你的模型。这是唯一一件"开工前必须补"的资产。

## 12. 美术标准：**占位级**（2026-10-20 定）

> **"能用就行，先让它存在，后期优化时再美化。"**

这句话是项目的美术预算线，写死在这里，免得后面反复纠结。

**占位级要做到的（做到就够，不要再多做）：**

- 剪影对：一眼能看出是什么东西
- 比例对：按真实世界尺寸（米 / 厘米），跟角色和场景对得上
- 部件位置对：轮子在轮子该在的地方，接口在接口该在的地方
- 面数低：单件 **1 万面以内**
- 材质分槽对：能换色、能分材质的部分要分开
- **不做**：内饰、镂空、倒角细节、UV 展开、贴图绘制

**流程纪律**：Blender → `RawAssets\Exports\` **暂存** →（经确认后）→ 导入 UE。
**不允许跳过暂存区直接导入。**

### 第一条实例：货车（已完成，占位级通过）

| 项 | 值 |
|---|---|
| 源文件 | `RawAssets\Blender\Vehicles\BL_Truck.blend` |
| 预览图 | 同目录 `BL_Truck_preview_{34,front,side,rear}.png` |
| 导出 | `RawAssets\Exports\SM\SM_Truck.fbx`（240 KB） |
| 面数 | **8,147** |
| 物体 | **5 个**：`SM_Truck_Body` + `Wheel_FL/FR/RL/RR`（轮子独立、原点在轮心） |
| 尺寸 | 4.60 × 1.66 × 2.00 m，面朝 **+X**，原点在车底中心 |
| 材质槽 | 7 个：Body（换色用）/ Tire / Rim / Glass / Trim / Light / Plate / Chrome |
| UE 状态 | **未导入**（按要求停在暂存区） |

**建模过程中踩到的两个坑（留给后来人）：**

1. **布尔运算在合并后的网格上会炸。** 想在车身上切真轮拱，EXACT 求解器直接产出破碎几何。改用**外挂式轮眉**（圆弧薄片）绕过。
2. **`bpy.data.materials.get()` 会复用旧材质且不更新颜色。** Blender 会话里材质不随物体清除，所以改颜色一直不生效、车身永远是第一版的白。必须在 `mat()` 里**无条件重设** Base Color / Roughness / Metallic。

**能拼成网格的关键做法：**

1. 立方体每个面细分 **5×5**（`subdivide_edges` + `use_grid_fill`）；

## 16. 地表贴图补齐（回答"砾石为什么跑地下去了"）

### 问题本身是对的，但错在**顺序**

- **地下用砾石是对的**：砂金（placer gold）本来就是古河床富集的产物，金子比重大、被水冲走后沉在砾石层里。所以地下那层砾石**就是古河床**，玩家在那儿挖到含金砂完全说得通。
- **真错的是地表**：河床、矿砂堆用的还是纯棕色，而你生成这张图的初衷正是淘金场景 —— 结果它只出现在地下。

### 已修：同一张砾石贴图，做**湿 / 干两个变体**

| 材质 | 用在哪 | 处理 |
|---|---|---|
| `M_RiverBed_Gravel_Wet` | `SM_RiverBed` | 染色压暗到 0.42、粗糙度 ×0.38（水膜反光）、密度 0.35（≈2.8 m 一格） |
| `M_Paydirt_Gravel` | `SM_Paydirt_S/M/L` | 染色 0.78、粗糙度 ×1.10（干燥）、密度 1.10 |
| `M_Terrain_Soil` | `SM_Terrain_30m_01..03` | 土壤贴图，密度 0.18（≈5.5 m 一格，大地表不能太密） |
| `M_RockDebris_Granite` | `SM_RockDebris_01..04` | 花岗岩压暗 0.62，密度 1.60 |

### 踩的坑：**隐藏物体上的 UV 算子是静默失败的**

地表这几件一开始贴图完全不生效，表面一片纯色。原因不是贴图密度，而是：

> 前一步为了渲染预览把它们 `hide_set(True)` 了，之后 `bpy.ops.uv.cube_project` 在**隐藏物体上不报错、也不干活**，UV 全是零 —— 整个面采样同一个像素，看起来就是纯色。

修法：**展开 UV 前必须先 `hide_set(False)` / `hide_viewport = False`**。

排查办法：打印 UV 的 min/max。全零或全相同就是没展开成功。

### 贴图密度不能一刀切

`cube_project` 是 **1 个 UV 单位 = 1 米**，再乘 Mapping 的 Scale：

| 物体尺寸 | 合适的 Scale | 一格覆盖 |
|---|---|---|
| 1 m 岩壁格 | 1.4 | 0.71 m |
| 0.4 m 矿砂堆 | 1.1 | 0.9 m |
| 6 × 30 m 河床 | **0.35** | 2.8 m |
| 30 × 30 m 地形 | **0.18** | 5.5 m |

**判断标准**：贴图上的颗粒在最终画面里应该约等于真实尺寸。砾石颗粒约 5 cm，若 Scale 给到 1.8（每米 1.8 次），颗粒只有 5 mm，远处直接被 mipmap 糊成纯色。

## 22. C++：梯子攀爬（第二刀）

矿洞是竖的，没有攀爬玩家根本下不去，所以这是核心移动能力里最该先补的一块。

### 新增

| 文件 | 内容 |
|---|---|
| `DGLadder.h/.cpp` | `ADGLadder`：占位梯子网格 + 攀爬触发体积 |
| `DGCharacter` | 攀爬状态机：`bIsClimbing` / `EnterClimb` / `ExitClimb` / `UpdateClimbing` |
| `DGGameMode` | 开局额外生成**攀爬测试台**：3 m 平台 (700,-400) + 梯子 (540,-400) |
| `DGHUD` | 攀爬时显示 `CLIMBING  W up / S down` / `Space jump off` |

### 行为规则（对齐 PRD §8）

| 规则 | 实现 |
|---|---|
| **爬梯不受负重影响** | 攀爬速度用**常量** `ClimbSpeed = 190`，不走 `GetSpeedMultiplier()` |
| 走进梯子范围按前进键自动攀爬 | 重叠体积 + `ForwardInput > 0.15` 触发 |
| W/S 上/下 | 直接改 Actor Z，并夹在 `[bottom+40, top-20]` |
| 到顶继续按 W → 翻上平台 | 触顶时 `ExitClimb` + `LaunchCharacter` 前上方冲量 |
| 空格跳离 | `ExitClimb` + 前上冲量 |

攀爬时把 `MovementMode` 切成 `MOVE_Flying` 且 `MaxFlySpeed = 0`——重力关闭、但位移完全由 `UpdateClimbing` 接管，避免"飞行 + 手动位移"双重驱动。

### 踩的坑：**子组件会继承父组件的拉伸缩放**

第一版把 `ClimbVolume` 挂在 `Frame` 下面，而 `Frame` 被缩放成 `(0.2, 0.08, 3.2)` 来做梯子外形。结果：

- 体积半尺寸 45×45×160 被乘成 **9 × 3.6 × 512**
- 相对位置 Z=160 也被乘成 **512**

**玩家永远触发不到攀爬**，而且体积飘在 5 米高空。

修法：加一个**不缩放的 `SceneRoot`** 当根节点，`Frame` 和 `ClimbVolume` 都挂在根下做兄弟节点——缩放只作用在视觉网格上。

> 通用教训：**任何要参与 gameplay 判定的组件（碰撞、触发、导航）都不要挂在会被拉伸的视觉组件下面。**

| 8 个类注册 | ✅ **8 / 8** |
| 梯子高 320 时 bottom/top | ✅ 100 / 420 |
| 触发体积世界半尺寸 | ✅ 45 × 45 × 160（缩放 1.0） |
| 体积垂直范围 vs 梯子范围 | ✅ 100..420 vs 100..420 **完全一致** |

## 23. 用真岩石资产替换引擎方块（2026-10-20 晚）

**背景：**用户指出——游戏里那面矿壁用的是引擎自带的方块 + 纯色材质，而岩壁格贴图资产早就做好了。这是偷懒，不是技术限制。

### 做了什么

| 步骤 | 内容 |
|---|---|
| 导入网格 | 5 个 FBX（`SM_Rock_<岩层>.fbx`）→ `/Game/DirtyGold/Art/Environment/Rocks` |
| 导入贴图 | 15 张（5 岩层 × BC/R/N）→ `/Game/DirtyGold/Art/Textures` |
| 建材质 | 5 个 `M_Rock_<岩层>` → `/Game/DirtyGold/Materials` |
| 改 C++ | `ADGMineCell` 按岩层加载对应网格 + 材质，不再用引擎 Cube |

### 材质结构

`BaseColor ← T_..._BC.RGB` / `Roughness ← T_..._R.R` / `Normal ← T_..._N.RGB`

采样器类型是关键：**BC 用 `SAMPLERTYPE_COLOR`、R 用 `SAMPLERTYPE_LINEAR_COLOR`、N 用 `SAMPLERTYPE_NORMAL`**。贴图本身的 sRGB 开关也做了对应设置（BC 开、R/N 关）。

### 矿格结构重构

原来：`Root = StaticMesh(引擎Cube)`，靠材质染色区分岩层。
现在：**`Root = BoxComponent(1 m 立方，BlockAll)`，`Mesh = StaticMeshComponent(NoCollision，纯显示)`**。

理由：岩石是不规则体，用 Box 当碰撞既便宜又稳定；也避免了"碰撞跟着网格走"带来的物理不确定性。

变体切换按世界坐标哈希取 `% 4`，整面墙不会长得一样。

### 验证

|---|---|
| 磁盘持久化 | 85 个 uasset（80 网格 + 5 材质实例） |

| 网格三角面 | 298 面 |
| 材质对应正确 | ✅ 5 / 5（`M_Rock_Gravel` 配 Gravel 网格） |

**① FBX 导入的资产不会自动落盘，而且丢了以后无法直接重导。**

第一次用 MCP 导入 `SM_Rock_Soil.fbx`，注册表里看到 17 个资产（12 网格 + 4 UCX + 1 材质），但**磁盘上只有那个材质实例**。我强制关闭编辑器后，网格全丢。

再导入时 UE 因为同名材质实例已存在而**跳过整个文件**，一个网格都不生成。

**② Static 组件在运行时不能换网格。**

## 24. 修用户实测反馈的四个问题（2026-10-20 晚）

用户进 PIE 实测后报的三个问题 + 一个隐性问题，逐条修。

### ① 矿石碎块没有贴图

**原因**：`ADGOreChunk` 一直在用引擎 Sphere + 纯色材质，从来没接资产。

**修法**：导入 `SM_Ore.fbx` → 用 `SM_Ore_01..03_LOD0` 真网格，并按含金量换材质：
- 含金 > 0.5 g → `M_Ore_Gold`（花岗岩贴图 × 暖金色）
- 否则 → `M_Ore_Rock`（花岗岩贴图原色）

两个材质都是新建的：花岗岩 BC/R/N + 采样器类型正确设置。

### ② 石头浮在半空

**原因**：测试矿壁硬编码在世界坐标 `(320, 0, 50)`。
而关卡里有 **64 个 Landscape 流送代理**——地形高度根本不是 0。所以整面墙悬在地形之上。

**修法**：`ADGGameMode` 开局从高空往下打射线找地形高度，**逐列取地面高度**（4 米宽的墙在斜坡上也不会一边悬空），墙底贴地生成。

同时发现关卡里**没有 PlayerStart**，玩家本来是生成在半空的——现在开局把 Pawn 也按地形高度落地。

### ③ 梯子看起来像绳索

**原因**：`ADGLadder` 的"梯子"是一根被拉伸的立方体（0.2 × 0.08 × 3.2 m），远看就是一根杆。

**修法**：导入 `SM_Ladder.fbx`，用 `SM_Ladder_LOD0` 真网格（两根立杆 + 10 根横档），按 `Height / 300` 缩放。

### ④ 爬到顶端上不去，卡在梯顶

**原因**（这是纯逻辑 bug）：位置被夹紧到 `Top - 20`，而翻越判定要求 `Loc.Z >= Top - 2`——**永远不可能成立**。

```cpp
Loc.Z = FMath::Clamp(..., Bottom, Top - 20);      // 最高只能到 Top-20
if (Loc.Z >= Top - 2)  { /* 翻上去 */ }            // 这个条件永远为假
```

## 25. 修"石头浮空"和"梯子交互"（2026-10-20 深夜）

用户实测反馈两条硬伤，根因都查清了。

### ① 石头浮空 —— 位置被烘进了网格

**现象**：看得见的石头飘在半空摸不到，能摸到的是地面上一个看不见的碰撞盒。

**根因**：Blender 里为了渲预览图，把每个岩壁格摆到了墙上（`location = (-1.5, 0, 3.5)` 之类），**然后直接用这些带位置的物体导出 FBX**。UE 导入后网格顶点本身带偏移，而 `ADGMineCell` 的碰撞盒在 Actor 原点 —— 于是视觉和碰撞错开几米。

**实测偏移**：花岗岩 `(-1.5, 0, +3.5)` 米；土壤 `(-1.5, 0, +0.5)` 米。

**修法**：写 `clean_export.py`，导出前把**所有网格物体的 location / rotation / scale 全部清零**，再用命令行背景模式（`blender -b`）重新导出全部资产。

**验证**：重新导入后逐网格检查包围盒中心，**20 个岩石网格全部居中在 ±3 cm 内**。
（矿石和梯子的中心不在原点，那是**故意**的——它们的原点在底面，用于贴地摆放。）

> **教训（写死）**：**任何要进 UE 的 FBX，导出前必须清零物体变换。** 预览用的摆放位置绝不能留在导出物上。

## 26. 再修：下梯子 + 矿石专属贴图（2026-10-20 深夜二）

### ① 矿石"贴图都一样"

**根因**：矿石根本没有专属贴图。我图省事，让 `M_Ore_Rock` / `M_Ore_Gold` 都复用了**花岗岩**贴图，只靠颜色乘法区分 —— 所以矿石和矿壁长得一样。

**修法**：用花岗岩照片**生成一张专属矿石贴图**：
1. 母岩压暗去饱和（矿脉嵌在暗色围岩里）
2. 用 fbm 噪声取高值区做**石英脉**（亮白斑块）
3. 撒 90 颗**金斑**
4. 再从这张图推法线（强度 14）和粗糙度

产出 `T_Ore_Quartz_BC/N/R`，导入后**原地重建**两个材质（不删除，因为已被引用，删除会失败）。

### ② 下不了梯子

**根因（两条）**：

**a. 站在平台上够不到梯子。**
`FindClimbableLadder` 之前只认准心射线命中的梯子。站上平台后，射线被平台自身挡住，打不到梯子，E 就变成"捡矿"。

修法：加兜底 —— 射线没命中时，**找 200 cm 内最近的梯子**。

**b. `ForwardInput` 会卡住。**
Enhanced Input 的 `Triggered` 只在按住时触发，**松开不再触发**，于是 `ForwardInput` 永远停在上一次的值。攀爬时按过 W 再松开，人会一直往上飘；按 S 反而可能被覆盖。

修法：绑定 `Completed` / `Canceled` → `OnMoveForwardReleased()` 把 `ForwardInput` 归零。

**另外两处顺带调整**：
- 梯子高度 320 → **380**（平台 300），顶端露出 80 cm，站平台上能看见也能瞄到
- 攀爬下降下限从 `底+40` 抬到 **`底+90`**（角色胶囊半高），避免沉进地面

## 27. 真因：材质编译失败 → UE 静默回退默认材质（棋盘格）

用户第二次反馈"还是原来的贴图"。这次抓到了引擎的真实错误。

### 根因

引擎日志（通过 MCP 的 `warnings` 字段才看到）：

```
Failed to compile Material for platform PCD3D_SM6, Default Material will be used in game.
(Node TextureSample) Sampler type is 线性颜色, should be 遮罩 for T_Rock_Soil_R
```

**粗糙度贴图是 `TC_MASKS`（遮罩）压缩，但材质里那个 TextureSample 节点的采样器类型被我设成了 `SAMPLERTYPE_LINEAR_COLOR`（线性颜色）。** 两者不匹配 → 材质编译失败 → **UE 运行时静默回退到默认材质**，显示成那身米色棋盘格。

**关键教训：材质编译失败不会报错弹窗，只会打一条 LogMaterial 警告，然后照样"能用"——用默认材质。** 所以从画面上看就是"贴图没生效"，而查组件属性会显示材质**已经正确挂上**（我上一轮就是被这个骗了）。

### 修法

重建全部 7 个材质（5 岩石 + 2 矿石），粗糙度节点的采样器类型改为 **`SAMPLERTYPE_MASKS`**：

| 节点 | 贴图压缩 | 正确采样器 |
|---|---|---|
| BC | TC_DEFAULT | `SAMPLERTYPE_COLOR` |
| R | TC_MASKS | **`SAMPLERTYPE_MASKS`** ← 原来是 LINEAR_COLOR |
| N | TC_NORMALMAP | `SAMPLERTYPE_NORMAL` |

**验证方式**：调用 `recompile_material` 后检查返回值里的 `warnings`，确认没有 `Failed to compile`。—— 而不是只查"材质有没有挂上"。

### 顺带修的两处

| 对象 | 问题 | 修法 |
|---|---|---|
| 梯子 | `Frame` 从来没指定材质，用的是 FBX 自带默认材质 | 指定 `M_Wood_Placeholder`（土壤贴图压棕） |
| 攀爬平台 | 引擎方块，**根本没有材质槽内容** | 指定 `M_Rock_Granite`，看起来像石台 |

### 仍然存在的问题

**关卡的 Landscape 也没有地形材质**——场景地面同样显示成棋盘格。这是关卡本身的问题（模板关卡没配 LandscapeMaterial），和岩石材质无关，需要单独做一个地形材质。

### 方法教训（写给以后的自己）

1. **判断材质是否生效，不能只看组件上的引用，要看有没有编译警告。**
2. 贴图的压缩格式、采样器类型、sRGB 三者必须配套，错一个就静默失败。
3. 引擎"静默回退默认材质"这个行为会让排查方向完全跑偏（会误以为是资产没导入、绑定没生效）。

## 28. 梯子吸附（2026-10-20 深夜三）

用户要求：**E 在梯顶也要能交互**，并且**起跳碰到梯子要自动吸附**。

### 为什么梯顶按 E 没反应

`FindClimbableLadder` 用的是 **3D 距离**（`FVector::DistSquared`）判断 200 cm 半径。
站到梯子顶端时，角色和梯子 Actor（原点在**底面**）的垂直差就是 380 cm —— **早就超出半径，永远找不到梯子**。

### 修法

**① 换成"水平距离 + 高度跨度"判定**（`IsWithinLadderReach`）：
- 水平距离 ≤ 220 cm
- 角色 Z 落在 `[梯底 - 150, 梯顶 + 220]` 之间

这样站在梯底、梯中、梯顶，甚至站在平台上，都能命中同一把梯子。

**② 起跳/坠落时自动吸附**：
`UpdateClimbing` 在非攀爬状态下检查 `IsFalling()`，若水平距离 ≤ 110 cm 且落在梯子跨度内 → 直接 `EnterClimb`。

**③ 加 0.7 秒冷却**：
否则空格跳开后，人在半空仍贴着梯子，会**立刻被吸回去**。`ExitClimb` 里设 `ClimbCooldown = 0.7`，自动吸附要等冷却结束。

**④ 吸附时把高度夹进跨度**：
`EnterClimb` 里把 Z 夹到 `[底+90, 顶-10]`，从空中吸附时不会落到梯子外面。

### ① 手持姿态：抬到手视野内

|---|---|---|---|

### ② 挥镐：以握把为轴向下砸

**关键前提**：`SM_Pickaxe` 的**网格原点就是握把端**，所以只要旋转组件，镐头自然绕握把划弧，握把不动——不需要骨骼。

动作曲线（手调的分段 lerp）：

1. `0 → StrikeAt(0.45)`：抬起，俯仰 `0 → +34°`
2. `0.45 → 0.72`：砸下，`+34 → −26°`

## 34. 镐头接口修正 + 淘金盘上移（2026-10-21 凌晨五）

### 镐头为什么"看着别扭"

**根因**：杆到末端时本身**下弯了约 10.6°**（曲线 `z = -0.085t² + 0.008t`），而镐头是**轴对齐**装的。两者差 10.6°，接口就是斜的。

**修法**：算杆端的切线角 `θ = atan2(-dz/dt, dx/dt)`，把整个镐头绕 Y 轴、以`(HX, 0, HZ)`为轴心转 θ，让它和杆对齐。

**另外两侧镐臂改回完全对称**（等长 0.255、等下垂 0.055、同样收尖），之前一端 1.3 倍高、一端 0.25 长，看着一高一低。

### 淘金盘上移

`ToolBaseLoc.Z` 从 −34 抬到 **−22**，倾角 −58° → −56°，盘口更朝向相机。

镐子倾角也从 85° 调到 **80°**（略微前倾，不那么笔直）。

## 35. 镐头的"下垂方向"错了 —— 按参考图修正（2026-10-21 凌晨六）

用户指出：**镐臂的下垂方向应该和镐把一致**（尖端朝下），实际镐子是拿尖端凿，不是平着拍。

### 根因

我原来把镐臂的下垂做在 **−Z 方向**：

```python
z = HZ - droop * (t ** 1.5)     # 错
```

但网格的 +X 是"握把→镐头"，游戏里把镐子竖起来是绕 Y 轴 Pitch ≈ 80°，此时**局部 Z 变成了朝向玩家的水平方向**。结果镐臂朝玩家弯，第一人称看就是"镐头平着拍"。

**正确方向是 −X**（指向握把）——竖起来之后 −X 正好是**正下方**，尖端因此朝下，挥镐时是尖端先着地。

```python
x = HX - droop * (t ** 1.5)     # 对
z = HZ
```

下垂量也加大到 **7.5 cm**，弧度更明显。

### 淘金盘凹面朝向

用户要求"凹的一侧对着玩家，像端碗"。淘金盘模型里**盘口朝 +Z**。要让 +Z 转向相机（−X），绕 Y 轴 Pitch ≈ **−90°**。

由 −56° 改为 **−78°**，位置 (48, 0, −20)，缩放 1.05。

### 验证

| 检查 | 结果 |
|---|---|
| 全量编译 | ✅ `Succeeded` |
| 镐子三个 LOD 落盘 | ✅ `disk=True` ×3 |
| 镐头对称 | ✅ bbox `y ±0.301` |

### 结构上的教训

**给"竖直握持"的武器建模时，先想清楚局部坐标到屏幕坐标的映射**：
- 局部 +X（握把→头）= 屏幕上= 上
- 局部 −X = 屏幕下
- 局部 ±Y = 屏幕左右
- 局部 ±Z = 屏幕前后（朝玩家/背离玩家）

所以"往下垂"必须做在 **−X** 上，做在 −Z 上会变成"朝玩家弯"。
