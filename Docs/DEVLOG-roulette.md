# 轮盘赌：从"怎么改都不对"到"几何真值"的排查记录

> 记录一次真实的 bug 排查：**判定的颜色和小球实际停的颜色对不上**。
> 从 6 个错误方案走到最终方案，结论是——**判定不该"推算"，应该直接读几何**。
> 对应代码：`Source/study/RouletteTable.h / .cpp`

---

## 0. 最终方案（一句话）

> 球停稳后，用它**相对转子的角度**去查一张由转子网格**三角形**生成的
> 「角度 → 颜色」表（360 格，1° 一格）。

红 / 黑 / 绿在模型里是三个独立材质（`MAT_lacquer_red / black / green`），
所以 `BeginPlay` 时逐三角形算它在盘面上的角度，按材质归类，就能把整圈颜色读出来。
**判定和画面使用同一份几何数据，不存在"推算"环节。**

判定采用三级回退，日志会写明用的是哪一级：

| 级别 | 数据来源 | 前提 | 日志 |
|---|---|---|---|
| ① | 几何颜色表 | 无（推荐） | `来源=几何表` |
| ② | 球下方射线读材质 | 轮盘网格有碰撞体 | `来源=盘面材质` |
| ③ | 号码序列 + 角度映射 | 手工校准过 | `来源=角度映射` |

---

## 1. 症状

玩家押红/黑/绿，小球停在某一格，但结算的颜色经常对不上：

- 球压在**红格**，结果显示**黑**
- 12 把里有 2 把错，比例不稳定
- 越靠近两格分界线，越容易错

---

## 2. 六个弯路（按时间顺序）

### ① 假设"0 号格在 0°，号码按 0→36 顺时针排"

**做法**：`结果 = 号码表[round(球角度 / (360/37))]`

**为什么错**：真实轮盘的号码顺序是打乱的
（`0, 32, 15, 19, 4, 21, 2, 25, …`），而且"0 号格朝哪个方向"完全由模型作者决定。

**证据**：球在黑格，结果报红。

---

### ② 单点校准 `PocketZeroYaw`（手工填偏移角）

**做法**：让玩家转一把，看到球下实际是几号，反推偏移量。

**为什么错**：一个样本只能解出**偏移**，解不出**方向**。
而真实轮盘的格子是**红黑隔格交替**的 —— 差一格（`360/37 ≈ 9.73°`）
就等于**颜色整体反一次**，所以表现为"红黑全反"。

**证据**：人工试了多组角度，仍然是反的。

---

### ③ 两点校准（偏移 + 方向一起解）

**做法**：收两个样本，令 `实测角度 = Z + d × 格号 × 9.73°`，
对 `d = ±1` 分别求 `Z`，取两个样本能对齐的那个方向。

**评价**：数学上是对的，日志里也能打出残差。但它**依然依赖**
"号码顺序必须是标准轮盘顺序"这个假设，而且需要玩家自己读数。
作为兜底保留（第 ③ 级），不再作为主方案。

---

### ④ 射线读球下方的材质

**做法**：球停稳后从球心向下打一条线，读命中面的材质名 → 颜色。

**为什么错**：**轮盘网格没有碰撞体**（导入时关闭了"自动生成碰撞"），
射线直接穿过盘面打在**地板**上。

**决定性证据**（这条日志一句话排除了整条路线）：

```
[Roulette] 采样 0：Actor=Floor_0 组件=StaticMeshComponent0 元素=1 材质=null 命中点=(25.7, 17.3, -0.5)
```

`Z = -0.5` = 地面。之后代码改成"从**被打中的组件**取材质"（而不是从自己的 RotorMesh 取），
避免张冠李戴，但**没有碰撞体这条路线就走不通**，于是默认关闭。

---

### ⑤ 先定号码，再让盘/球"凑"到那一格

**做法**：先随机抽一个格号，然后转子转过去，让中奖格停在球下面。

**为什么错**：**因果反了**。设计上要求"球停在哪一格，那一格就是结果"，
而"先定结果再让画面去凑"必然出现"瞄准了却停偏"的情况。
改成：球落在随机角度 → 由落点反推结果。

---

### ⑥ 几何颜色表（第一版）——两个自己写的 bug

**做法**：扫转子网格的三角形，算每个三角形的角度/半径，按材质统计，
生成「角度 → 颜色」表。

**为什么没生效**：两个 bug 同时存在。

| # | Bug | 后果 |
|---|---|---|
| 1 | `FMath::UnwindDegrees` 返回 **(-180, 180]**，代码直接 `Clamp(..., 0, 359)` | 所有负角度被压在 **0° 格**，表全错 |
| 2 | 材质名匹配要求必须包含 `lacquer` | 运行时材质名对不上 → 一条都没匹配到 → **表根本没建起来** |

日志里 `来源=角度映射` 就是"表没生效"的线索。

**修复**：

```cpp
// 角度必须先搬进 [0, 360)
float Deg = FMath::RadiansToDegrees(FMath::Atan2(Y, X));
Deg = FMath::Fmod(Deg + 360.f, 360.f);
```

并放宽材质匹配（`red` / `green` / `black`，排除 `black_steel`），
同时把**每个材质槽、每一段的材质名和三角形数**都打进日志。

**结果**：`来源=几何表`，颜色判定从此与画面一致。

## 3. 根因归纳

| 层次 | 根因 |
|---|---|
| 设计层 | 把"表现"当成了数据源：用角度**推算**格号，再查号码表。任何一处假设错位（起点、方向、顺序）都会错 |
| 实现层 | `UnwindDegrees` 的返回区间用错；材质名匹配过严 |
| 排查层 | 失败分支没有日志 → 只能靠猜。转折点是那行 `Actor=Floor_0` |

**教训**：判定和表现必须共享同一份数据。
几何表就是把"画面上的颜色"变成了**可以被判定的数据**。

## 4. 最终实现要点

### 4.1 颜色表生成（`BuildColorTableFromMesh`）

```
对 LOD0 的每个 Section：
    取材质名 → 红 / 黑 / 绿（排除白条、黑钢、木头）
    对该 Section 的每个三角形：
        质心 (X, Y) → 角度 deg（Fmod 到 0..360）、半径 R
        R < 1cm 的（中轴）跳过
        投票：Votes[颜色][floor(deg)]++
对 360 个 bin 取票数最多的颜色 → ColorByAngle[360]
覆盖率 > 180° 才算建表成功
```

顺带算出三种颜色的平均半径（作为 `BallInnerCm` 的默认值）。

### 4.2 球落点

```
盘转几圈（纯视觉，与结果无关）
球落在随机角度 ← 这一步就是"开奖"
把落点吸附到格子正中心（bSnapBallToPocketCenter）
    原因：球直径 4cm，而一格弧长只有 5.3cm，
          不吸附就会"视觉压左、判定取右"
由落点反推格号 → 号码（只用于日志，不显示给玩家）
```

### 4.3 结算

```
停稳 → 查几何表拿颜色 → 与押注比较 → 加/减钱
扣钱在开转前，加钱在停稳后（视觉与到账同一刻）
```

## 5. 关键参数（`RouletteTable` 的 Details 面板）

| 参数 | 值 | 说明 |
|---|---|---|
| `bSnapBallToPocketCenter` | ✅ 开 | 球落格心，避免压线歧义 |
| `bReadColorFromSurface` | ⬜ 关 | 需要轮盘有碰撞体才能用 |
| `bSwapRedBlack` | ⬜ 关 | 红黑对调（调试用；几何表生效后不需要） |
| `BallOuterCm / BallInnerCm / BallHeightCm` | 按网格自动算 | 球道半径与高度（cm） |
| `GreenMultiplier` | 20 | 押绿命中返还倍数（真实轮盘是 36） |
| `SpinDuration / RotorTurns` | 5 秒 / 4 圈 | 观感 |

## 7. 已知限制 / 后续

| 项 | 说明 |
|---|---|
| **报不出具体号码** | 号码是贴图，代码读不到像素。要报号码只有两条路：① 在 DCC 里把 36 格拆成 36 个材质；② 提供"0 号格中心在转子本地坐标的角度" |
| 绿 20 倍的期望 | 54.1%（庄家优势 46%）。标准轮盘是 36 倍 = 97.3% |
| 球是代码轨迹，不是物理球 | 要真实弹跳需另做：物理球 + 结束前 0.8 秒吸附落格 |
| 轮盘网格没有碰撞体 | 所以射线方案不可用；补上碰撞后 `bReadColorFromSurface` 即可启用 |
| 玩家交互 | 复用了 `AMerchant` 的对话框系统（`EMerchantKind::Roulette`），走近按 E |

---

## 8. 三条可复用的经验

1. **表现和判定必须共用一份数据。** 靠"推算"就一定会错位。
2. **`FMath::UnwindDegrees` 返回 (-180, 180]。** 当索引/直方图用之前必须搬到 [0, 360)。
3. **每一条失败分支都要打日志。** 这次真正的转折点是
   `Actor=Floor_0 命中点 Z=-0.5` —— 一行日志排除了整条技术路线。
